## 4. Rollback
Order matters; every step is a person's action, nothing runs by itself.
1. **Dashboard: remove `fanday` from the exposed schemas first** (so the Data API stops serving it before anything is dropped). Check: `GET /rest/v1/leagues` with `Accept-Profile: fanday` now fails.
2. Delete the 5 Edge Functions and the 11 `FANDAY_` secrets (dashboard/CLI), so no new sign-ins or calls arrive.
3. **Preview, approve, run.** (a) `scripts/shared-impact/rollback-preview.sql` (read-only, as postgres): lists the auth users that would be deleted, with email, sign-in methods, why each qualifies and that none owns rows outside `fanday`; also the users that will be kept and the Apple identities that will be unlinked. (b) **Babar or Misha read that list and approve it** by running its last result, the generated `approval_sql` (it writes only inside `fanday`). (c) `scripts/shared-impact/rollback.sql` (one transaction). It deletes only approved users, refuses and drops nothing if an eligible user is missing from the approved list, keeps and reports any Fanday-created user who owns another app's rows, unlinks only Apple identities Fanday added, then drops `fanday`.
4. Dashboard: remove the two redirect URLs, delete the appended Google client IDs (keep the original first ID untouched), switch Apple off.
5. Rerun `check-other-apps.sh`: must equal the baseline (apple false again).
No cleanup is needed in `supabase_migrations` because nothing was written there.

## 6. What is NOT zero-impact (plainly)
1. **The shared user list.** Every Fanday sign-in adds a row to `auth.users` (+ `auth.identities`), visible to anyone with dashboard access to this project. Today: 2 users. If a Fanday user's Google or Apple email matches a Woofabulary user they become one account (GoTrue links by verified email; behaviour on this project unverified). Accounts Fanday made are removable; merged ones are only unlinked.
2. **Project-wide toggles:** Apple provider and the Google client-ID list. Both revert cleanly and Woofabulary shows no change, but they are shared settings.
3. **Shared auth limits.** Per Supabase docs read 2026-11-05 (this project's dashboard values unverified): token refresh 1,800/hour and verify 360/hour *per IP* (burst 30); OTP sends 360/hour and auth emails (custom SMTP) 30/hour *project-wide*. Per-IP counters are separate per IP, so Fanday and Woofabulary collide only on one shared address (office, carrier NAT, a bot). Fanday does not call `/auth/v1/otp` (its link comes from our function), so it should not touch the project-wide OTP/email budget: **unverified; test once after step 5.**
4. **Shared compute and plan.** Pro plan; DB 19 MB; max 60 connections (13 in use when read); `shared_buffers` 224 MB, which looks like a small instance (size not readable here). Fanday adds a daily ingest, a game-day recheck and per-user calls. Edge invocations, egress and monthly usage are **not readable** with my tools; the Pro limits I remember (8 GB DB, 250 GB egress, 2M function calls, 100k monthly users) are **unverified**. Misha: read Dashboard > Usage before, and after the first week.
5. **Email-link abuse (M2).** Anyone can ask `fanday-send-link` for a link to any address. Caps: 10/hour per caller, 3/hour per address, 20/hour overall, one alert email an hour; counters hold no addresses. So at most 480 emails a day and up to 480 new `auth.users` rows a day, and a stranger gets a Fanday email. Gmail's own cap (about 500/day) is the outer limit. The overall cap also lets an attacker block everyone's Fanday links for an hour: a Fanday availability trade-off, not a Woofabulary one, whose email sign-in is a separate path.
6. **Account deletion** removes the auth user only if Fanday created it and it owns nothing elsewhere (checked twice). A tiny race remains if that person starts using Woofabulary between check and delete (their Woofabulary rows would cascade away): unverified, very unlikely.
7. **Other.** Backups and point-in-time restore cover all apps together; a restore rewinds Fanday and the others. Security advisors will list new warnings for the anon-callable `fanday` functions (by design). Anon-readable `fanday` tables will probably show in the GraphQL endpoint (unverified, read-only). Apply and rollback both fire the DDL watchers (section 1, row 5).

8. **Service-role exposure (residual risk).** `fanday-send-link` and `fanday-delete-account` hold the shared project's **service-role key** (they need Auth admin: create users, generate links, delete users). A compromise of either function, or of anything it imports, would expose that key and with it every table of Woofabulary and Chess Tutor, not just Fanday. Reduced, not removed: `fanday-ingest`, `fanday-go` and `fanday-device` do **not** hold it (publishable key + per-function secret checked inside the RPC against a hash in `fanday.function_secrets`; a test fails if another function starts naming the service-role key). Every import is pinned: `supabase-js` `https://esm.sh/@supabase/supabase-js@2.118.0?pin=v140` (its own dependencies are exact versions), `jsr:@supabase/functions-js@2.118.0`, `denomailer@1.6.0`; `scripts/test-function-keys.mjs` fails on any unpinned import. No `deno.lock` could be generated (Deno is not installed here), so the lock is by exact pins only. **Denomailer 1.6.0 source read 2026-11-05** (17 files, tree sha256 `912f5ea43a314aece1fd7947b7a1f8f4edde0cc8206eca46223922862b0896d6`): its only external import is `deno.land/std@0.173.0/encoding/base64.ts`, and the only network calls are `Deno.connect` / `Deno.connectTls` to the SMTP host; no `fetch`, `eval` or file access. Residual: esm.sh and deno.land are third-party hosts; a supply-chain attack on a pinned version's host is not ruled out. A true fix is a separate project (section 7).
9. **Google client-ID list order.** Woofabulary's Google button uses the *first* client ID in the field. Appending Fanday's IDs after it is safe; any edit that puts Fanday's ID first, re-sorts the list or trims the old one would break Woofabulary sign-in at once. Mitigation: screenshot before; the `authorize(google) client_id` line in `check-other-apps.sh` must be identical after; undo is deleting the appended IDs. Only Misha edits the field.
10. **Shared logs.** Edge Function logs, API logs and Postgres logs are one stream for the whole project. Fanday's functions log no email addresses, tokens or links (they log error messages only, by design), and the daily ingest adds a few hundred log lines a day. But anyone who can read this project's logs can see Fanday's request metadata (paths, status codes, IP addresses as the platform records them) next to the other apps', and log retention is the plan's, not Fanday's. Limits of the logs themselves were not readable here: unverified.
11. **pg_graphql (live 1.5.11).** pg_graphql follows SQL privileges (pg_graphql security docs: revoking SELECT removes a table from the visible schema), not the Data API's exposed-schemas list. Fanday gives `anon` SELECT on its 5 public reference tables, so they will very likely also be queryable at `/graphql/v1` (public data, the same rows REST serves). The 11 anon-callable functions may appear there too; each is gated by a token or a secret exactly as over REST, so GraphQL adds no new access. **Not verified** (pg_graphql is absent from the local image and I do not write to the live project). Prevention: `fanday_0001` sets `comment on schema fanday is '@graphql({"introspection": false})'` (introspection is off by default; this makes it explicit; it hides the schema from introspection only, not from queries). Fully removing the tables from GraphQL would need revoking anon SELECT, which would break REST. Check after step 4: as anon, POST `{ leaguesCollection { edges { node { id } } } }` to `/graphql/v1`; if the result is unwanted, decide then.
